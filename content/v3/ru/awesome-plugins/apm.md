# Документация FlightPHP APM

Добро пожаловать в FlightPHP APM — персонального тренера по производительности вашего приложения! Это руководство — ваша дорожная карта для настройки, использования и освоения мониторинга производительности приложений (APM) с FlightPHP. Ищете ли вы медленные запросы или просто хотите изучить графики задержек — мы вас прикроем. Сделаем ваше приложение быстрее, пользователей счастливее, а отладку — лёгкой!

Посмотрите [демо](https://flightphp-docs-apm.sky-9.com/apm/dashboard) панели мониторинга для сайта документации Flight.

![FlightPHP APM](/images/apm.png)

## Почему APM важен

Представьте: ваше приложение — оживлённый ресторан. Без способа отслеживать, сколько времени занимают заказы и где кухня буксует, вы лишь гадаете, почему клиенты уходят недовольными. APM — это ваш су-шеф: он следит за каждым шагом, от входящих запросов до запросов к базе данных, и отмечает всё, что вас замедляет. Медленные страницы отталкивают пользователей (исследования говорят, что 53% уходят, если сайт загружается дольше 3 секунд!), и APM помогает выявить эти проблемы *до* того, как они станут болезненными. Это проактивное спокойствие — меньше моментов «почему это сломано?», больше побед «как здорово всё работает!».

## Установка

Начнём с Composer:

```bash
composer require flightphp/apm
```

Вам понадобятся:
- **PHP 7.4+**: обеспечивает совместимость с LTS-дистрибутивами Linux и поддержку современного PHP.
- **[FlightPHP Core](https://github.com/flightphp/core) v3.15+**: лёгкий фреймворк, который мы улучшаем.

## Поддерживаемые базы данных

FlightPHP APM в настоящее время поддерживает следующие базы данных для хранения метрик:

- **SQLite3**: простая, файловая, отлично подходит для локальной разработки или небольших приложений. Вариант по умолчанию в большинстве установок.
- **MySQL/MariaDB**: идеально для крупных проектов или производственных сред, где нужно надёжное масштабируемое хранилище.

Вы можете выбрать тип базы данных на этапе настройки (см. ниже). Убедитесь, что в вашем окружении PHP установлены необходимые расширения (например, `pdo_sqlite` или `pdo_mysql`).

## Начало работы

Вот пошаговая инструкция к величию APM:

### 1. Регистрация APM

Добавьте это в ваш `index.php` или в файл `services.php`, чтобы начать отслеживание:

```php
use flight\apm\logger\LoggerFactory;
use flight\database\SimplePdo;
use flight\Apm;

$ApmLogger = LoggerFactory::create(__DIR__ . '/../../.runway-config.json');
$Apm = new Apm($ApmLogger);
$Apm->bindEventsToFlightInstance($app);

// Если вы добавляете подключение к базе данных
// Предпочтительно использовать SimplePdo (или PdoQueryCapture из Tracy Extensions в разработке).
// Включите отслеживание запросов APM через массив параметров (5-й аргумент).
$pdo = new SimplePdo('mysql:host=localhost;dbname=example', 'user', 'pass', null, [
	'trackApmQueries' => true, // требуется для сбора запросов для APM
]);
$Apm->addPdoConnection($pdo);
```

**Что здесь происходит?**
- `LoggerFactory::create()` получает вашу конфигурацию (подробнее об этом чуть позже) и настраивает логгер — по умолчанию SQLite.
- `Apm` — главный герой: он прослушивает события Flight (запросы, маршруты, ошибки и т.д.) и собирает метрики.
- `bindEventsToFlightInstance($app)` связывает всё это с вашим приложением Flight.

**Совет: Сэмплирование**
Если ваше приложение нагружено, регистрация *каждого* запроса может перегрузить систему. Используйте коэффициент выборки (от 0.0 до 1.0):

```php
$Apm = new Apm($ApmLogger, 0.1); // Логирует 10% запросов
```

Это сохраняет отзывчивость и при этом даёт надёжные данные.

### 2. Настройка

Запустите эту команду, чтобы создать `.runway-config.json`:

```bash
php vendor/bin/runway apm:init
```

**Что это делает?**
- Запускает мастер, который спрашивает, откуда берутся сырые метрики (источник) и куда попадают обработанные данные (назначение).
- По умолчанию используется SQLite — например, `sqlite:/tmp/apm_metrics.sqlite` для источника и ещё один для назначения.
- В итоге вы получите конфигурацию примерно такую:
  ```json
  {
    "apm": {
      "source_type": "sqlite",
      "source_db_dsn": "sqlite:/tmp/apm_metrics.sqlite",
      "storage_type": "sqlite",
      "dest_db_dsn": "sqlite:/tmp/apm_metrics_processed.sqlite"
    }
  }
  ```

> В процессе также будет вопрос о запуске миграций для этой настройки. Если вы настраиваете всё впервые, ответьте «да».

**Зачем два хранилища?**
Сырые метрики накапливаются быстро (представьте нефильтрованные логи). Воркер обрабатывает их в структурированное назначение для панели мониторинга. Всё остаётся аккуратным!

### 3. Обработка метрик с помощью воркера

Воркер превращает сырые метрики в данные, готовые для панели мониторинга. Запустите его один раз:

```bash
php vendor/bin/runway apm:worker
```

**Что он делает?**
- Читает из вашего источника (например, `apm_metrics.sqlite`).
- Обрабатывает до 100 метрик (размер пакета по умолчанию) в ваше назначение.
- Останавливается, когда закончил, или если метрик больше нет.

**Постоянная работа**
Для живых приложений вам потребуется непрерывная обработка. Вот ваши варианты:

- **Режим демона**:
  ```bash
  php vendor/bin/runway apm:worker --daemon
  ```
  Работает бесконечно, обрабатывая метрики по мере поступления. Отлично для разработки или небольших установок.

- **Crontab**:
  Добавьте это в ваш crontab (`crontab -e`):
  ```bash
  * * * * * php /path/to/project/vendor/bin/runway apm:worker
  ```
  Запускается каждую минуту — идеально для продакшена.

- **Tmux/Screen**:
  Запустите отсоединяемую сессию:
  ```bash
  tmux new -s apm-worker
  php vendor/bin/runway apm:worker --daemon
  # Ctrl+B, затем D для отсоединения; `tmux attach -t apm-worker` для повторного подключения
  ```
  Продолжает работать, даже если вы выйдете из системы.

- **Свои настройки**:
  ```bash
  php vendor/bin/runway apm:worker --batch_size 50 --max_messages 1000 --timeout 300
  ```
  - `--batch_size 50`: Обрабатывать по 50 метрик за раз.
  - `--max_messages 1000`: Остановиться после 1000 метрик.
  - `--timeout 300`: Завершиться через 5 минут.

**Зачем это нужно?**
Без воркера ваша панель мониторинга пуста. Это мост между сырыми логами и практическими выводами.

### 4. Запуск панели мониторинга

Увидьте ключевые показатели вашего приложения:

```bash
php vendor/bin/runway apm:dashboard
```

**Что это?**
- Запускает PHP-сервер на `http://localhost:8001/apm/dashboard`.
- Показывает журнал запросов, медленные маршруты, частоту ошибок и многое другое.

**Настройка**:
```bash
php vendor/bin/runway apm:dashboard --host 0.0.0.0 --port 8080 --php-path=/usr/local/bin/php
```
- `--host 0.0.0.0`: доступен с любого IP (удобно для удалённого просмотра).
- `--port 8080`: используйте другой порт, если 8001 занят.
- `--php-path`: укажите путь к PHP, если его нет в PATH.

Откройте URL в браузере и исследуйте!

#### Производственный режим

В продакшене вам, возможно, придётся перепробовать несколько способов запуска панели мониторинга, поскольку обычно действуют брандмауэры и другие меры безопасности. Вот несколько вариантов:

- **Используйте обратный прокси**: настройте Nginx или Apache для перенаправления запросов на панель мониторинга.
- **SSH-туннель**: если у вас есть SSH-доступ к серверу, используйте `ssh -L 8080:localhost:8001
ваш_пользователь@ваш_сервер`, чтобы пробросить панель на ваш локальный компьютер.
- **VPN**: если сервер находится за VPN, подключитесь к нему и откройте панель напрямую.
- **Настройте брандмауэр**: откройте порт 8001 для вашего IP или сети сервера (или тот порт, который вы задали).
- **Настройте Apache/Nginx**: если перед вашим приложением стоит веб-сервер, вы можете настроить его на домен или поддомен. Направьте этот хост на `dashboard/index.php` (встроенный сервер использует его как роутер). Статические файлы находятся рядом в `dashboard/css` и `dashboard/js`.
- **Базовая аутентификация**: задайте `apm.dashboard_auth.user` и `apm.dashboard_auth.password` в конфигурации runway. Если любое из значений пустое, панель остаётся открытой. Это единый общий пароль, а не учётные записи пользователей приложения.

#### Нужна другая панель?

Вы можете создать собственную панель мониторинга, если хотите! Посмотрите в каталоге vendor/flightphp/apm/src/apm/presenter идеи о том, как представлять данные для собственной панели!

## Возможности панели мониторинга

Панель открывается с цифр, затем идут графики, затем журнал запросов.

- **Строка статистики**: количество запросов, частота ошибок, p95, p99, средняя задержка, пропускная способность в минуту и частота попаданий в кэш.
- **Отставание воркера**: сколько сырых метрик всё ещё находится в `apm_metrics_log`. Большое число означает, что воркер не успевает. Пустая панель с отставанием 0 означает, что данные ещё не собраны.
- **График задержки**: средняя задержка и количество запросов за одинаковые интервалы. За последний час используются 5-минутные интервалы, за последний день — 15-минутные, за последнюю неделю — 6-часовые. Пользовательский диапазон выбирает интервал, сохраняющий около 40 точек. Время хранится в UTC и отображается в выбранном вами часовом поясе.
- **График статусов**: сгруппированные счётчики `2xx`, `3xx`, `4xx` и `5xx`. Нажмите на серию, чтобы отфильтровать журнал по этому классу.
- **Медленные маршруты, middleware, запросы и запросы HTTP**: по пять каждого. Запросы к БД группируются, так что `WHERE id = 1` и `WHERE id = 2` считаются одним оператором. Нажмите на маршрут, медленный запрос или группу ошибок, чтобы отфильтровать журнал.
- **Пользовательские события**: каждый тип пользовательского события, которое запускает ваше приложение, с его количеством, временем последнего появления и небольшим графиком тренда за выбранный период. Сортировка по количеству. Учитываются временной диапазон, скрытие ботов и другие фильтры. Нажмите на тип, чтобы отфильтровать журнал по нему.
- **Журнал запросов**: метод, URL, статус, время, память, хост и флаг бота. Детали загружаются при открытии строки и включают временную шкалу, представления, параметры запроса, трассировку ошибки и пользовательские события.
- **Скрыть ботов**: исключает трафик ботов из агрегированных данных и журнала. Поисковые роботы и LLM-краулеры (GPTBot, ClaudeBot, PerplexityBot, SearxNG и другие) помечаются как боты.
- **Пользовательский диапазон**: выберите окно «от/до» в дополнение к последнему часу, дню или неделе.
- **Фильтры**: URL, статус, ID запроса, маршрут, IP, хост, сессия, user agent, тип пользовательского события, данные события и сообщение об ошибке. Строка запроса сохраняет их после обновления страницы.

**Пример**:
Запрос к `/users` может показать:
- Общее время: 150мс
- Middleware: `AuthMiddleware->handle` (50мс)
- Запрос: `SELECT * FROM users` (80мс)
- Время рендеринга представления
- Кэш: попадание в `user_list` (5мс)

## Добавление пользовательских событий

Отслеживайте что угодно — например, вызов API или процесс оплаты:

```php
use flight\apm\CustomEvent;

$app->eventDispatcher()->trigger('apm.custom', new CustomEvent('api_call', [
    'endpoint' => 'https://api.example.com/users',
    'response_time' => 0.25,
    'status' => 200
]));
```

**Где это появляется?**
В деталях запроса на панели мониторинга в разделе «Пользовательские события» — раскрывается с красивым JSON-форматированием. Панель **Пользовательские события** также подсчитывает каждый тип для вас, так что короткого события `docs.markdown_served` достаточно, чтобы ответить на вопрос «как часто это происходит?».

**Пример использования**:
```php
$start = microtime(true);
$apiResponse = file_get_contents('https://api.example.com/data');
$app->eventDispatcher()->trigger('apm.custom', new CustomEvent('external_api', [
    'url' => 'https://api.example.com/data',
    'time' => microtime(true) - $start,
    'success' => $apiResponse !== false
]));
```
Теперь вы увидите, тормозит ли это API ваше приложение!

## Мониторинг базы данных

Отслеживайте PDO-запросы так:

```php
use flight\database\SimplePdo;

$pdo = new SimplePdo('sqlite:/path/to/db.sqlite', null, null, null, [
	'trackApmQueries' => true, // требуется для сбора запросов для APM
]);
$Apm->addPdoConnection($pdo);
```

**Что вы получаете**:
- Текст запроса (например, `SELECT * FROM users WHERE id = ?`)
- Время выполнения (например, 0.015с)
- Количество строк (например, 42)
