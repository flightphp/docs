# Конфігурація

## Огляд

Flight надає простий спосіб налаштувати різні аспекти фреймворку відповідно до потреб вашого застосунку. Деякі з них налаштовані за замовчуванням, але ви можете змінити їх за потреби. Ви також можете встановлювати власні змінні для використання у всьому застосунку.

Чітка багаторівнева конфігурація (файлові значення за замовчуванням + секрети з оточення) також допомагає [AI-інструментам кодування](/learn/ai): агенти вивчають одне місце для літералів і одне для секретів, замість того щоб вигадувати читання `$_ENV` у контролерах.

## Розуміння

Ви можете налаштувати певну поведінку Flight, встановлюючи значення конфігурації через метод `set`.

```php
Flight::set('flight.log_errors', true);
```

У структурованому застосунку (зокрема у [скелетоні](https://github.com/flightphp/skeleton)) ви зазвичай завантажуєте налаштування проєкту з `app/config/config.php`, а потім застосовуєте відповідні ключі до Engine (наприклад, `flight.base_url`, `flight.views.path`). Також можна впроваджувати невеликий об'єкт конфігурації в контролери, замість того щоб читати глобальні значення всюди — це зручніше для тестів і для агентів, які дотримуються `AGENTS.md`.

## Основне використання

### Параметри конфігурації Flight

Нижче наведено перелік усіх доступних параметрів конфігурації:

- **flight.base_url** `?string` - Перевизначте базову URL-адресу запиту, якщо Flight працює в підкаталозі. (за замовчуванням: null)
- **flight.case_sensitive** `bool` - Чутливе до регістру зіставлення URL-адрес. (за замовчуванням: false)
- **flight.handle_errors** `bool` - Дозволити Flight обробляти всі помилки внутрішньо. (за замовчуванням: true)
  - Якщо ви хочете, щоб Flight обробляв помилки замість стандартної поведінки PHP, це має бути true.
  - Якщо у вас встановлено [Tracy](/awesome-plugins/tracy), вам потрібно встановити це значення false, щоб Tracy міг обробляти помилки.
  - Якщо у вас встановлено плагін [APM](/awesome-plugins/apm), вам потрібно встановити це значення true, щоб APM міг журналювати помилки.
- **flight.log_errors** `bool` - Журналювати помилки у файл журналу помилок веб-сервера. (за замовчуванням: false)
  - Якщо у вас встановлено [Tracy](/awesome-plugins/tracy), Tracy журналюватиме помилки на основі конфігурацій Tracy, а не цієї конфігурації.
- **flight.debug** `bool` - Виводити детальну інформацію про помилку (повідомлення винятку, код і стек викликів) у браузері, коли виникає помилка. (за замовчуванням: false)
  - **Ніколи не вмикайте це у продакшні** — це розкриває внутрішні деталі застосунку. Використовуйте це лише для локальної розробки або стенду.
  - Коли `false`, замість цього показується загальна помилка `500 Internal Server Error`. Поєднуйте з `flight.log_errors`, щоб перехоплювати помилки на стороні сервера.
- **flight.allow_method_override** `bool` - Дозволити перевизначення HTTP-методу через заголовок запиту `X-HTTP-Method-Override` або поле `_method` у тілі POST-запиту. (за замовчуванням: true)
  - **Рекомендується встановити це значення `false`** для застосунків, яким не потрібне підроблення методу на основі HTML-форми, оскільки це запобігає підробленню клієнтами запитів `DELETE` або `PUT` через звичайну POST-форму.
  - Дивіться [Безпека](/learn/security#flight-configuration-hardening) для отримання додаткових деталей.
- **flight.views.path** `string` - Каталог, що містить файли шаблонів подань. (за замовчуванням: ./views)
- **flight.views.extension** `string` - Розширення файлів шаблонів подань. (за замовчуванням: `.php`; офіційний скелетон встановлює `.twig` при використанні Twig)
- **flight.views.restrict_to_path** `bool` - Коли `true`, рідний `View` у Flight приймає лише файли шаблонів, які розташовані всередині `flight.views.path`. (за замовчуванням: `false`). **Увімкніть це** для застосунків, які використовують рідні подання. Дивіться [Безпека](/learn/security#flightviewsrestrict_to_path).
- **flight.content_length** `bool` - Встановлювати заголовок `Content-Length`. (за замовчуванням: true)
  - Якщо ви використовуєте [Tracy](/awesome-plugins/tracy), це потрібно встановити false, щоб Tracy міг правильно відображатися.
- **flight.v2.output_buffering** `bool` - Використовувати застаріле буферизування виводу. Дивіться [перехід до v3](migrating-to-v3). (за замовчуванням: false)

### Конфігурація завантажувача

Існує також додатковий параметр конфігурації для завантажувача. Він дозволяє автоматично завантажувати класи з `_` у назві класу.

```php
// Увімкнути завантаження класів із підкресленнями
// За замовчуванням true
Loader::$v2ClassLoading = false;
```

Пам'ятайте, що [автозавантаження](/learn/autoloading) також залежить від **регістру назв папок**, які мають відповідати вашим просторам імен — особливо зі схемою скелетона `App\` + `app/Controller/`.

### Конфігурація проєкту та `.env` (шаблон скелетона)

Ядро Flight не вимагає файлів `.env`. Багато застосунків використовують лише PHP-масив конфігурації. Офіційний скелетон розшаровує конфігурацію так, щоб секрети залишалися поза git, а Runway міг безпечно перезаписувати **літеральну** конфігурацію:

1. **`.env` / реальне оточення** — секрети та перевизначення для розгортання (ігнорується git).
2. **`app/config/config.php`** — літеральні PHP-масиви за замовчуванням (копіюються з `config_sample.php`). Надавайте перевагу **відсутності** виразів `$_ENV[...]` у цьому файлі: такі інструменти, як `runway config:set`, можуть перезаписати його статичними значеннями та вбудувати секрети у файл.
3. **Об'єднання під час завантаження** — оточення має пріоритет для зіставлених ключів; код застосунку читає об'єкт конфігурації або `$app->get()`, а не `$_ENV` у контролерах.

Приклад структури `config_sample.php` / `config.php` (спрощено):

```php
<?php
// Тільки літерали — секрети належать до .env для робочого процесу скелетона
return [
	'app' => [
		'env' => 'development',
		'debug' => true,
		'base_url' => '/',
		'timezone' => 'UTC',
	],
	'database' => [
		'driver' => 'sqlite', // або mysql, або '' для вимкнення
		'host' => 'localhost',
		'dbname' => '',
		'user' => '',
		'password' => '',
		'file_path' => __DIR__ . '/../../database.sqlite',
	],
	// ...
];
```

```bash
# .env.example → .env (скелетон)
APP_ENV=development
APP_DEBUG=true
FLIGHT_BASE_URL=/
DB_DRIVER=sqlite
# DB_PASSWORD=...
```

Такий поділ є навмисним для [AI-дружніх проєктів](/learn/ai): інструкції можуть говорити «значення за замовчуванням у `config.php`, секрети в `.env`, впроваджуйте Config / Engine — ніколи не вигадуйте доступ до оточення в контролері». Існуючі застосунки можуть повністю ігнорувати `.env` і зберігати єдиний файл конфігурації.

### Змінні

Flight дозволяє зберігати змінні, щоб їх можна було використовувати будь-де у вашому застосунку.

```php
// Збережіть вашу змінну
Flight::set('id', 123);

// В іншому місці вашого застосунку
$id = Flight::get('id');
```

Щоб перевірити, чи змінну було встановлено, ви можете зробити так:

```php
if (Flight::has('id')) {
  // Зробіть щось
}
```

Ви можете очистити змінну ось так:

```php
// Очищує змінну id
Flight::clear('id');

// Очищує всі змінні
Flight::clear();
```

> **Примітка:** Те, що ви можете встановити змінну, не означає, що це варто робити. Використовуйте цю функцію помірковано. Причина в тому, що будь-що, збережене тут, стає глобальною змінною. Глобальні змінні є поганими, оскільки їх можна змінити з будь-якого місця у вашому застосунку, що ускладнює пошук помилок. Крім того, це може ускладнити такі речі, як [модульне тестування](/guides/unit-testing). Віддавайте перевагу впровадженню через конструктор (як у скелетоні з налаштуванням Dice) для сервісів і конфігурації, які потрібні контролерам.

### Помилки та винятки

Усі помилки та винятки перехоплюються Flight і передаються методу `error`, якщо `flight.handle_errors` встановлено true.

Типова поведінка — надсилати загальну відповідь `HTTP 500 Internal Server Error` з певною інформацією про помилку.

Ви можете [перевизначити](/learn/extending) цю поведінку відповідно до своїх потреб:

```php
Flight::map('error', function (Throwable $error) {
  // Обробити помилку
  echo $error->getTraceAsString();
});
```

За замовчуванням помилки не журналюються на веб-сервері. Ви можете увімкнути це, змінивши конфігурацію:

```php
Flight::set('flight.log_errors', true);
```

#### 404 Не знайдено

Коли URL-адресу не знайдено, Flight викликає метод `notFound`. Типова поведінка — надсилати відповідь `HTTP 404 Not Found` з простим повідомленням.

Ви можете [перевизначити](/learn/extending) цю поведінку відповідно до своїх потреб:

```php
Flight::map('notFound', function () {
  // Обробити ситуацію, коли не знайдено
});
```

## Усунення неполадок
- Якщо у вас виникають проблеми з визначенням усіх значень вашої конфігурації, ви можете виконати `var_dump(Flight::get());`
- Якщо Runway або інструменти розгортання перезаписали `config.php`, переконайтеся, що секрети не було закомічено — тримайте їх у `.env` або в реальному оточенні, якщо ви використовуєте шаблон скелетона.
