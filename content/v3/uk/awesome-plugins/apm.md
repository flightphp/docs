# Документація FlightPHP APM

Ласкаво просимо до FlightPHP APM — вашого персонального коуча з продуктивності застосунку! Цей посібник — ваш путівник із налаштування, використання та опанування моніторингу продуктивності застосунків (APM) із FlightPHP. Чи ви полюєте на повільні запити, чи просто хочете помилуватися графіками затримок — ми подбали про вас. Зробімо ваш застосунок швидшим, користувачів щасливішими, а сеанси налагодження — легшими!

Перегляньте [демо](https://flightphp-docs-apm.sky-9.com/apm/dashboard) дашборда для сайту Flight Docs.

![FlightPHP APM](/images/apm.png)

## Чому APM важливий

Уявіть: ваш застосунок — це завантажений ресторан. Без способу відстежувати, скільки часу займають замовлення або де кухня гальмує, ви лише здогадуєтесь, чому клієнти йдуть незадоволеними. APM — ваш су-шеф: він стежить за кожним кроком, від вхідних запитів до запитів до бази даних, і позначає все, що вас сповільнює. Повільні сторінки втрачають користувачів (дослідження кажуть, що 53% відвідувачів ідуть, якщо сайт завантажується понад 3 секунди!), а APM допомагає виявити ці проблеми *до* того, як вони завдадуть шкоди. Це проактивний спокій — менше моментів “чому це зламалося?”, більше перемог “подивіться, як гладко це працює!”.

## Встановлення

Почніть із Composer:

```bash
composer require flightphp/apm
```

Вам знадобиться:
- **PHP 7.4+**: Зберігає сумісність із LTS-дистрибутивами Linux, підтримуючи сучасний PHP.
- **[FlightPHP Core](https://github.com/flightphp/core) v3.15+**: Легкий фреймворк, який ми покращуємо.

## Підтримувані бази даних

FlightPHP APM наразі підтримує такі бази даних для зберігання метрик:

- **SQLite3**: Проста, файлова та чудово підходить для локальної розробки або невеликих застосунків. Типовий варіант у більшості конфігурацій.
- **MySQL/MariaDB**: Ідеальна для більших проєктів або продакшн-середовищ, де потрібне надійне й масштабоване сховище.

Ви можете вибрати тип бази даних на етапі конфігурації (див. нижче). Переконайтеся, що ваше PHP-середовище має необхідні розширення (наприклад, `pdo_sqlite` або `pdo_mysql`).

## Початок роботи

Ось ваш покроковий шлях до досконалого APM:

### 1. Зареєструйте APM

Додайте це у ваш `index.php` або файл `services.php`, щоб почати відстеження:

```php
use flight\apm\logger\LoggerFactory;
use flight\database\SimplePdo;
use flight\Apm;

$ApmLogger = LoggerFactory::create(__DIR__ . '/../../.runway-config.json');
$Apm = new Apm($ApmLogger);
$Apm->bindEventsToFlightInstance($app);

// Якщо ви додаєте підключення до бази даних
// Надавайте перевагу SimplePdo (або PdoQueryCapture з Tracy Extensions у режимі розробки).
// Увімкніть відстеження запитів APM через масив опцій (5-й аргумент).
$pdo = new SimplePdo('mysql:host=localhost;dbname=example', 'user', 'pass', null, [
	'trackApmQueries' => true, // потрібно для захоплення запитів для APM
]);
$Apm->addPdoConnection($pdo);
```

**Що тут відбувається?**
- `LoggerFactory::create()` отримує вашу конфігурацію (докладніше незабаром) і налаштовує логер — за замовчуванням SQLite.
- `Apm` — головний герой: він слухає події Flight (запити, маршрути, помилки тощо) і збирає метрики.
- `bindEventsToFlightInstance($app)` прив’язує все це до вашого застосунку Flight.

**Порада: семплінг**
Якщо ваш застосунок завантажений, логування *кожного* запиту може перевантажити систему. Використовуйте частоту семплінгу (від 0.0 до 1.0):

```php
$Apm = new Apm($ApmLogger, 0.1); // Логує 10% запитів
```

Це зберігає швидкодію, водночас даючи вам надійні дані.

### 2. Налаштуйте це

Виконайте це, щоб створити ваш `.runway-config.json`:

```bash
php vendor/bin/runway apm:init
```

**Що це робить?**
- Запускає майстер, який запитує, звідки надходять необроблені метрики (джерело) і куди надсилаються оброблені дані (призначення).
- За замовчуванням SQLite — наприклад, `sqlite:/tmp/apm_metrics.sqlite` для джерела, інший файл для призначення.
- У результаті ви отримаєте конфігурацію на кшталт:
  ```json
  {
    "apm": {
      "source_type": "sqlite",
      "source_db_dsn": "sqlite:/tmp/apm_metrics.sqlite",
      "storage_type": "sqlite",
      "dest_db_dsn": "sqlite:/tmp/apm_metrics_processed.sqlite"
    }
  }
  ```

> Цей процес також запитає, чи хочете ви запустити міграції для цього налаштування. Якщо ви налаштовуєте це вперше, відповідь — так.

**Чому два місця?**
Необроблені метрики швидко накопичуються (згадайте невідфільтровані логи). Воркер обробляє їх у структуроване призначення для дашборда. Це допомагає підтримувати порядок!

### 3. Обробляйте метрики за допомогою воркера

Воркер перетворює необроблені метрики на дані, готові для дашборда. Запустіть його один раз:

```bash
php vendor/bin/runway apm:worker
```

**Що він робить?**
- Читає з вашого джерела (наприклад, `apm_metrics.sqlite`).
- Обробляє до 100 метрик (типовий розмір пакета) у ваше призначення.
- Зупиняється після завершення або якщо метрик не залишилося.

**Підтримуйте його роботу**
Для живих застосунків вам знадобиться безперервна обробка. Ось ваші варіанти:

- **Режим демона**:
  ```bash
  php vendor/bin/runway apm:worker --daemon
  ```
  Працює безстроково, обробляючи метрики в міру надходження. Чудово для розробки або невеликих конфігурацій.

- **Crontab**:
  Додайте це до вашого crontab (`crontab -e`):
  ```bash
  * * * * * php /path/to/project/vendor/bin/runway apm:worker
  ```
  Спрацьовує щохвилини — ідеально для продакшену.

- **Tmux/Screen**:
  Запустіть від’єднувану сесію:
  ```bash
  tmux new -s apm-worker
  php vendor/bin/runway apm:worker --daemon
  # Ctrl+B, потім D, щоб від’єднатися; `tmux attach -t apm-worker`, щоб знову підключитися
  ```
  Підтримує роботу, навіть якщо ви вийдете з системи.

- **Власні налаштування**:
  ```bash
  php vendor/bin/runway apm:worker --batch_size 50 --max_messages 1000 --timeout 300
  ```
  - `--batch_size 50`: Обробляти 50 метрик за раз.
  - `--max_messages 1000`: Зупинитися після 1000 метрик.
  - `--timeout 300`: Вийти через 5 хвилин.

**Навіщо це потрібно?**
Без воркера ваш дашборд порожній. Він є мостом між необробленими логами та практичними висновками.

### 4. Запустіть дашборд

Перегляньте ключові показники вашого застосунку:

```bash
php vendor/bin/runway apm:dashboard
```

**Що це таке?**
- Запускає PHP-сервер за адресою `http://localhost:8001/apm/dashboard`.
- Показує логи запитів, повільні маршрути, рівні помилок тощо.

**Налаштуйте це**:
```bash
php vendor/bin/runway apm:dashboard --host 0.0.0.0 --port 8080 --php-path=/usr/local/bin/php
```
- `--host 0.0.0.0`: Доступний з будь-якої IP-адреси (зручно для віддаленого перегляду).
- `--port 8080`: Використовуйте інший порт, якщо 8001 зайнятий.
- `--php-path`: Вкажіть шлях до PHP, якщо його немає у вашому PATH.

Відкрийте URL у браузері та досліджуйте!

#### Режим продакшену

Для продакшену вам, можливо, доведеться спробувати кілька технік, щоб запустити дашборд, оскільки там, імовірно, є фаєрволи та інші заходи безпеки. Ось кілька варіантів:

- **Використовуйте зворотний проксі**: Налаштуйте Nginx або Apache для переспрямування запитів до дашборда.
- **SSH-тунель**: Якщо ви можете підключитися до сервера через SSH, використайте `ssh -L 8080:localhost:8001
youruser@yourserver`, щоб тунелювати дашборд на вашу локальну машину.
- **VPN**: Якщо ваш сервер за VPN, підключіться до нього та отримайте доступ до дашборда напряму.
- **Налаштуйте фаєрвол**: Відкрийте порт 8001 для вашої IP-адреси або мережі сервера (або будь-якого порту, який ви встановили).
- **Налаштуйте Apache/Nginx**: Якщо перед вашим застосунком є вебсервер, ви можете налаштувати його на домен або піддомен. Спрямуйте цей хост на `dashboard/index.php` (вбудований сервер використовує його як роутер). Статичні файли лежать поруч у `dashboard/css` та `dashboard/js`.
- **Базова автентифікація**: встановіть `apm.dashboard_auth.user` і `apm.dashboard_auth.password` у конфігурації runway. Якщо будь-яке зі значень порожнє, дашборд залишається відкритим. Це один спільний пароль, а не облікові записи користувачів застосунку.

#### Хочете інший дашборд?

Ви можете створити власний дашборд, якщо хочете! Перегляньте директорію vendor/flightphp/apm/src/apm/presenter, щоб отримати ідеї, як подавати дані для вашого власного дашборда!

## Функції дашборда

Дашборд відкривається з чисел, потім графіків, потім логу запитів.

- **Рядок статистики**: кількість запитів, рівень помилок, p95, p99, середня затримка, пропускна здатність за хвилину та частка влучань у кеш.
- **Черга воркера**: скільки необроблених метрик ще лежить у `apm_metrics_log`. Велике число означає, що воркер відстає. Порожній дашборд із чергою 0 означає, що нічого не зібрано.
- **Графік затримки**: середня затримка та кількість запитів для однакових інтервалів. Остання година використовує 5-хвилинні інтервали, останній день — 15-хвилинні, останній тиждень — 6-годинні. Власний діапазон вибирає інтервал, який зберігає близько 40 точок. Час зберігається в UTC і відображається в обраній вами часовій зоні.
- **Графік статусів**: стекові підрахунки `2xx`, `3xx`, `4xx` і `5xx`. Натисніть на серію, щоб відфільтрувати лог до цього класу.
- **Повільні маршрути, middleware, запити до бази даних і запити**: по п’ять кожного. Запити групуються так, що `WHERE id = 1` і `WHERE id = 2` вважаються одним виразом. Натисніть на маршрут, повільний запит або групу помилок, щоб відфільтрувати лог.
- **Користувацькі події**: кожен тип користувацької події, який запускає ваш застосунок, з його кількістю, часом останнього появи та маленькою лінією тренду для вибраного вікна. Відсортовано за кількістю. Враховує часовий діапазон, параметр Hide bots та інші фільтри. Натисніть на тип, щоб відфільтрувати лог за ним.
- **Лог запитів**: метод, URL, статус, час, пам’ять, хост і прапорець бота. Деталі завантажуються, коли ви відкриваєте рядок, і включають смугу таймінгу, представлення, параметри запиту, трасування помилки та користувацькі події.
- **Приховати ботів**: виключає трафік ботів з агрегатів і логу. Пошукові краулери та LLM-краулери (GPTBot, ClaudeBot, PerplexityBot, SearxNG та інші) позначено як ботів.
- **Власний діапазон**: виберіть вікно від/до додатково до останньої години, дня або тижня.
- **Фільтри**: URL, статус, ID запиту, маршрут, IP, хост, сесія, user agent, тип користувацької події, дані події та повідомлення про помилку. Рядок запиту зберігає їх після оновлення.

**Приклад**:
Запит до `/users` може показати:
- Загальний час: 150ms
- Middleware: `AuthMiddleware->handle` (50ms)
- Запит: `SELECT * FROM users` (80ms)
- Час рендерингу представлення
- Кеш: влучання в `user_list` (5ms)

## Додавання користувацьких подій

Відстежуйте будь-що — наприклад, виклик API або процес оплати:

```php
use flight\apm\CustomEvent;

$app->eventDispatcher()->trigger('apm.custom', new CustomEvent('api_call', [
    'endpoint' => 'https://api.example.com/users',
    'response_time' => 0.25,
    'status' => 200
]));
```

**Де це відображається?**
У деталях запиту дашборда в розділі “Custom Events” — розгортається з гарним форматуванням JSON. Панель **Користувацькі події** також рахує кожен тип за вас, тож швидкої події `docs.markdown_served` достатньо, щоб відповісти на запитання “як часто це відбувається?”.

**Варіант використання**:
```php
$start = microtime(true);
$apiResponse = file_get_contents('https://api.example.com/data');
$app->eventDispatcher()->trigger('apm.custom', new CustomEvent('external_api', [
    'url' => 'https://api.example.com/data',
    'time' => microtime(true) - $start,
    'success' => $apiResponse !== false
]));
```
Тепер ви побачите, чи цей API гальмує ваш застосунок!

## Моніторинг бази даних

Відстежуйте PDO-запити так:

```php
use flight\database\SimplePdo;

$pdo = new SimplePdo('sqlite:/path/to/db.sqlite', null, null, null, [
	'trackApmQueries' => true, // потрібно для захоплення запитів для APM
]);
$Apm->addPdoConnection($pdo);
```

**Що ви отримуєте**:
- Текст запиту (наприклад, `SELECT * FROM users WHERE id = ?`)
- Час виконання (наприклад, 0.015s)
- Кількість рядків (наприклад, 42)

**Зверніть увагу**:
- **Необов’язково**: Пропустіть це, якщо вам не потрібне відстеження БД.
- **SimplePdo (бажано)**: Використовуйте `SimplePdo` з `trackApmQueries => true`. Застарілий `PdoWrapper` усе ще працює (5-й аргумент конструктора `true`). Сирий основний PDO ще не підключено — слідкуйте за оновленнями!
- **Попередження про продуктивність**: Логування кожного запиту на сайті з великим навантаженням на БД може сповільнити роботу. Використовуйте семплінг (`$Apm = new Apm($ApmLogger, 0.1)`), щоб зменшити навантаження.

**Приклад виводу**:
- Запит: `SELECT name FROM products WHERE price > 100`
- Час: 0.023s
- Рядки: 15

## Опції воркера

Налаштуйте воркер на свій смак:

- `--timeout 300`: Зупиняється через 5 хвилин — добре для тестування.
- `--max_messages 500`: Обмежує до 500 метрик — робить роботу скінченною.
- `--batch_size 200`: Обробляє 200 за раз — балансує швидкість і пам’ять.
- `--daemon`: Працює без зупинки — ідеально для живого моніторингу.

**Приклад**:
```bash
php vendor/bin/runway apm:worker --daemon --batch_size 100 --timeout 3600
```
Працює годину, обробляючи 100 метрик за раз.

## ID запиту в застосунку

Кожен запит має унікальний ID запиту для відстеження. Ви можете використовувати цей ID у своєму застосунку, щоб зіставляти логи та метрики. Наприклад, ви можете додати ID запиту на сторінку помилки:

```php
Flight::map('error', function($message) {
	// Отримати ID запиту із заголовка відповіді X-Flight-Request-Id
	$requestId = Flight::response()->getHeader('X-Flight-Request-Id');

	// Додатково ви можете отримати його зі змінної Flight
	// Цей метод погано працюватиме у swoole або інших асинхронних платформах.
	// $requestId = Flight::get('apm.request_id');
	
	echo "Error: $message (Request ID: $requestId)";
});
```

## Оновлення

Якщо ви оновлюєтеся до новішої версії APM, можливо, потрібно виконати міграції бази даних. Ви можете зробити це, виконавши таку команду:

```bash
php vendor/bin/runway apm:migrate
```
Це виконає всі міграції, потрібні для оновлення схеми бази даних до останньої версії.

**Примітка:** Якщо ваша база даних APM велика, ці міграції можуть виконуватися деякий час. Запускайте їх у період низького навантаження. Воркер може продовжувати працювати. Міграції індексів не переписують зібрані рядки.

### Оновлення після 0.5.2 (дашборд та індекси)

0.5.2 лише розширила виявлення ботів. Файли індексів нижче постачаються у випуску після 0.5.2.

Спочатку зробіть резервну копію бази даних призначення. Скопіюйте файл SQLite або зробіть `mysqldump` схеми MySQL/MariaDB.

```bash
composer update flightphp/apm
php vendor/bin/runway apm:migrate
```

Це застосовує:

- SQLite: `0006-dest-indexes.sql` (індекси `request_dt` було видалено, коли `0005` перебудувала `apm_requests`)
- MySQL/MariaDB: `0002-dest-indexes.sql` (`request_dt` та інші фільтри дашборда)

`apm:migrate` записує ім’я файлу й пропускає його наступного разу. Запускати двічі безпечно. `apm:purge` порівнює `request_dt` з відсіканням UTC, що відповідає способу зберігання рядків. Перше очищення після цього оновлення може зберігати інше вікно, якщо часовий пояс сервера раніше не був UTC.

`X-Flight-Request-Id` відповідає `request_token`, збереженому для цього запиту.

### Оновлення з 0.4.3 -> 0.5.0

Якщо ви оновлюєтеся з 0.4.3 до 0.5.0, вам потрібно виконати таку команду:

```bash
php vendor/bin/runway apm:config-migrate
```

Це перенесе вашу конфігурацію зі старого формату з файлом `.runway-config.json` до нового формату, який зберігає ключі/значення у файлі `config.php`.

## Очищення старих даних

Щоб підтримувати базу даних у порядку, ви можете очищати старі дані. Це особливо корисно, якщо ви запускаєте завантажений застосунок і хочете тримати розмір бази даних під контролем.
Ви можете зробити це, виконавши таку команду:

```bash
php vendor/bin/runway apm:purge
```
Це видалить із бази даних усі дані, старші за 30 днів. Ви можете змінити кількість днів, передавши інше значення в опцію `--days`:

```bash
php vendor/bin/runway apm:purge --days 7
```
Це видалить із бази даних усі дані, старші за 7 днів.

## Усунення несправностей

Застрягли? Спробуйте це:

- **Немає даних на дашборді?**
  - Чи запущений воркер? Перевірте `ps aux | grep apm:worker`.
  - Шляхи в конфігурації збігаються? Переконайтеся, що DSN у `.runway-config.json` вказують на реальні файли.
  - Запустіть `php vendor/bin/runway apm:worker` вручну, щоб обробити метрики, що очікують.

- **Помилки воркера?**
  - Загляньте у свої файли SQLite (наприклад, `sqlite3 /tmp/apm_metrics.sqlite "SELECT * FROM apm_metrics_log LIMIT 5"`).
  - Перевірте логи PHP на наявність трасувань стека.

- **Дашборд не запускається?**
  - Порт 8001 зайнятий? Використовуйте `--port 8080`.
  - PHP не знайдено? Використовуйте `--php-path /usr/bin/php`.
  - Фаєрвол блокує? Відкрийте порт або використовуйте `--host localhost`.

- **Занадто повільно?**
  - Знизьте частоту семплінгу: `$Apm = new Apm($ApmLogger, 0.05)` (5%).
  - Зменште розмір пакета: `--batch_size 20`.

- **Не відстежуються винятки/помилки?**
  - Якщо у вашому проєкті ввімкнено [Tracy](https://tracy.nette.org/), вона перекриє обробку помилок Flight. Вам потрібно вимкнути Tracy і переконатися, що встановлено `Flight::set('flight.handle_errors', true);`.

- **Не відстежуються запити до бази даних?**
  - Надавайте перевагу `SimplePdo` з `['trackApmQueries' => true]` як 5-м аргументом конструктора (масив опцій).
  - Якщо ви все ще використовуєте застарілий `PdoWrapper`, передайте `true` як 5-й аргумент.
  - Викличте `$Apm->addPdoConnection($pdo)` після створення підключення.
